# Loot, recycling and ammo boxes

Status: **implemented in Lua and data, checked offline only.** Whether the
game spawns a die set, and how often one is met, is
`REQUIRES FUTURE IN-GAME VERIFICATION` (section 5).

Vanilla facts below were read from the installed Build 42.20.4 files and are
marked **FILE** (a script or Lua file under `media/`), **JAR** (`javap` of
`projectzomboid.jar`) or **INFERRED**. `tests/vanilla_snapshot.lua` records
the ones the tests depend on; `tests/snapshot_vanilla.lua` regenerates it
from an install.

## 1. Die sets as loot

A die set is still forged (two steel bar quarters at a forge). It can now
also be found. Loot is a second way to the tool, not a replacement: every
recipe names the die set by item type and keeps it, so a found, a forged and
a debug-spawned die set are the same thing, and finding one opens no recipe
early (the Ammo Making levels are on the recipes, not on the tool).

### 1.1 How vanilla distributes loot

- FILE `lua/server/Items/ProceduralDistributions.lua`:
  `ProceduralDistributions.list.<Name> = { rolls = N, items = { "Item",
  weight, … } }`. 1,420 lists.
- FILE `lua/server/Items/Distributions.lua`: a room's container names lists
  (`procList = { { name = "GunStoreAccessories", min = 0, max = 1,
  weightChance = 40 }, … }`).
- JAR `IsoWorld` (world init): triggers `OnPreDistributionMerge`,
  `OnDistributionMerge`, `OnPostDistributionMerge`, then `OnInitWorld`, then
  calls `ItemPickerJava.Parse()`, which reads the Lua tables once. JAR
  `LuaEventManager.AddEvents` registers all three events before any Lua
  loads.
- JAR `ItemPickerJava.doRollItemInternal`: for each of
  `rolls * SandboxOptions.rollsMultiplier` rolls and each entry,
  `Rand.Next(10000) < getActualSpawnChance(...)`, and
  `getActualSpawnChance` is `(weight * 100 * lootModifier + zombieDensity) *
  lootMultiplier`. **A weight is the percent chance per roll** at default
  settings.
- JAR `ItemPickerJava.getLootType` / `Item.isToolLoot`: an item whose
  `DisplayCategory` is `Tool` is "Tool" loot. The die sets are, so the
  sandbox's tool-loot setting scales them.
- JAR `ItemPickerJava.ExtractContainersFromLua`: an entry is resolved with
  `ScriptManager.FindItem`; a name with a dot is a full type
  (`AmmoMaking.DieSet9mm`). An unknown one is logged (`ignoring invalid
  ItemPicker item type`) and skipped. Vanilla's own lists hold dotted names
  (`"Base.HempBagSeed"`).

**184 of the 1,420 lists are named by no container.** Among them the three
gun-store lists marked `-- DEPRECATED` (`GunStoreCounter`,
`GunStoreDisplayCase`, `GunStoreShelf`, all emptied), and others that look
usable and are not: `PoliceStorageAmmunition`, `MetalWorkerTools`,
`MechanicTools`, `PrisonArmoryShotguns`, `ArmyHangarTools`. An entry added
to one of those never spawns. The snapshot lists all 184; the tests refuse a
target that is among them, and the game-start check reports one that has
become unused or empty on the running build.

### 1.2 What the mod adds

`AC_Loot.lua` (shared). On `OnPreDistributionMerge` it appends each entry to
its list, once: an entry already present is left alone, so a second world
load in the same Lua state adds nothing. A list that does not exist is never
created. The handler is the only thing the file registers; nothing runs per
frame or per container.

All numbers are in one place: `AC_Loot.CONFIG.tierWeight` (the weight of a
tier), `AC_Loot.TARGETS` (the lists, each with a scale and the calibre
classes it takes) and `calibre.lootTier` in `AC_Calibres.lua`. A weight is
`tierWeight[calibre.lootTier] * scale`.

The chances are per container that vanilla fills from that list, at default
sandbox settings and before the zombie-density bonus. A container is filled
from one of several lists, and `GunStoreAccessories` is used for at most one
display case per store (`max = 1`), so a die set is a find, not a stock item:
roughly one gun store in five holds any die set at all.

For comparison, in the same lists: a reloading skill book weighs 1 to 0.2,
`x8Scope` 6, a punch set 2 to 8.

Limits `AC_Loot.validate()` enforces, so a typo cannot make die sets common:
no entry above weight 1, no list with more than 5 of die-set weight in all,
no die set in more than four lists, every calibre in at least one, every
tier and class known, no list targeted twice. A model it refuses registers
nothing.

### 1.3 What is deliberately not loot

No primer, case, cup, sheet, bullet or hull is added to any list. They are
what the player manufactures; spawning them would skip the chain. Their raw
materials are vanilla items that vanilla already distributes (FILE, live
lists only):

| Input | Where vanilla puts it |
|---|---|
| `Base.CopperScrap` | 24 lists (electrical, plumbing, engineering, junk) |
| `Base.Matches`, `Base.Matchbox` | 23 and 17 lists |
| `Base.Fertilizer` | 5 farming and gardening lists (`CrateFertilizer` 50) |
| `Base.Charcoal` | 3 lists (`CrateCharcoal` 50), and made from logs |
| `Base.SteelBarQuarter` | 7 workshop and factory lists |
| `Base.CapGunCap`, `Base.CapGunCapBox` (100 caps) | only `WildWestSheriffDesk` / `WildWestSheriffLocker` |
| `Base.GunPowder` | no loot list; foraging (`Trash` category) and `GatherGunpowder` |
| `Base.BrassScrap` | no live list; bin junk at 0.05 and a broken saxophone or trumpet (`OnBreak.BrassScrap`) |
| `Base.BrassIngot`, `Base.CopperIngot`, `Base.CopperOre` | no loot list |

Two consequences. Toy caps are a curiosity (one Wild West location), so
match heads are the working source of priming compound. And brass exists in
the world almost only as what the player smelts, which is what makes
recycling it worth having.

## 2. Brass recycling

Brass components the player no longer wants (case cups, small sheets, the
cases or hulls of a calibre they have stopped loading) can be hammered into
vanilla `Base.BrassScrap`, and ten brass scrap can be cast back into a
`Base.BrassIngot`. It is a way to get some brass back, not a reversal of
crafting.

### 2.1 What vanilla offers

- FILE `items/normal.txt`: `Base.BrassScrap` exists (`DisplayCategory =
  Material`, weight 0.5). FILE: no craftRecipe in the installed scripts
  takes it, and no live loot list holds it (section 1.3). The mod's
  material table has counted it as 10 units of brass, like copper and zinc
  scrap, since the metallurgy stage. No new scrap item is added.
- FILE `recipes/recipes_ammunition.txt`, `GatherGunpowder`: any item tagged
  `base:ammo` is destroyed for one use of `Base.GunPowder`. FILE: exactly
  the nine round items carry that tag, and no mod item does. So vanilla
  already takes a **finished round** apart, for powder only.
- FILE: there is no spent-casing, hull or primer item in vanilla
  (`SPENT_CASE_RESEARCH.md`).

- Scrapping is cold work on any surface with a hammer, kept
  (`MakingHammer_Surface`, the line and timed action of the cup and case
  recipes). One craft takes components of one brass size; a line accepts
  any mix of them. Components of the same brass content share a recipe, so
  there are three, generated from the calibre model: a new calibre's case
  joins the recipe of its size without an edit.
- The recast is the copper and zinc casting recipe with brass scrap in it:
  furnace, empty crucible, tongs and mold kept, four charcoal, ten scrap,
  one ingot. Nothing is lost there; the loss is in the scrapping.
- All numbers are in `AC_Recycling.CONFIG` (`batchUnits`, `scrapPerBatch`).

### 2.3 Rules, and how they are enforced

| Rule | Enforced by |
|---|---|
| Scrapping returns **half** of the brass, never more | `AC_Recycling.validate()` (game start and tests); `AC_Materials.checkConservation` refuses a recipe marked `loss` that comes out even |
| Recycling awards **0 Ammo Making XP** | `AC_Recycling.CONFIG.xp`, refused by `validate()` if not 0; the callback test asserts the XP log stays empty |
| Only plain brass goes in: no round, primer, bullet, shot, die set, powder | `validate()` refuses any input or output that is not in the plain-brass table |
| Every loop through the recipe graph loses metal | test: with the scrapping recipes removed the metal graph has no cycle, and each scrapping recipe strictly loses |
| Primers, powder and priming compound are untouched | test: no recycling recipe consumes or creates any |

What is deliberately **not** recycled:

- **Finished rounds.** Vanilla already takes one apart for powder. A second
  way out of a round would let the same round pay twice.
- **Primers.** Scrapping one would destroy priming compound for one or two
  units of brass.
- **Bullets and shot charges.** They are copper; two bullets are exactly one
  `Base.CopperScrap`, so a lossy recipe would have nothing sensible to
  return and a lossless one would be a reversal of crafting.

### 2.4 Why half

Recycling awards nothing, but a case that is scrapped can be formed again,
and forming awards XP. That cannot be prevented (a recast ingot is an
ingot) so it has to be unprofitable. The measure, per case:

- **regained**: the XP of making the case once (its share of sheet forging,
  cup punching, and forming) times `recovery / (1 - recovery)`, the most a
  case can return if it is scrapped and re-formed for ever;
- **forgone**: the XP the case would have earned by being loaded (its
  primer, bullet, powder and assembly).

At a recovery of one half, `regained` equals the XP of making the case once
and is below `forgone` for every calibre. At three fifths the 12 gauge hull
crosses over (6.4 against 5.9): scrapping hulls would train faster than
loading shells. The tests assert `regained < forgone` for every calibre, so
a change to the recovery, to an XP value or to a calibre that breaks it
fails the suite.

Measured in the simulation: thirty brass ingots formed into 9mm cases,
scrapped and recast until nothing is left take six round trips, end with 50
of 3,000 units of brass, and earn 2,065 XP against 1,050 for one pass. The
bound is a factor of two, reached only by destroying all the brass.

## 3. Ammo boxes: nothing to build

**Vanilla already boxes handloaded rounds. The mod adds no box recipe and no
box item**, and a test fails if one appears.

FILE `scripts/generated/recipes/recipes_ammunition.txt`, the one packing
recipe, in full:

```text
craftRecipe place_ammo_in_box
{
    timedAction = PlaceAmmoInBox,
    time = 15,
    category = Packing,
    Tags = InHandCraft,
    inputs
    {
        item 20 [Base.Bullets44;Base.308Bullets;25:Base.ShotgunShells;Base.556Bullets;50:Base.Bullets9mm;50:Base.Bullets45;50:Base.Bullets38;50:Base.Bullets357;Base.3030Bullets] mappers[ammoType] flags[AllowFavorite;InheritFavorite;IsExclusive],
    }
    outputs
    {
        item 1 mapper:ammoType,
    }
    itemMapper ammoType { Base.Bullets44Box = Base.Bullets44, … }
}
```

| Round | Box | Rounds per box | Carton (12 boxes) |
|---|---|---|---|
| `Base.Bullets9mm`, `Bullets38`, `Bullets45`, `Bullets357` | `…Box` | 50 | `…Carton` |
| `Base.Bullets44`, `556Bullets`, `3030Bullets`, `308Bullets` | `Bullets44Box`, `556Box`, `3030Box`, `308Box` | 20 | `…Carton` |
| `Base.ShotgunShells` | `ShotgunShellsBox` | 25 | `ShotgunShellsCarton` |

What follows from the files:

- **It matches by item type and nothing else.** One input line: the rounds.
  No empty box item, no tool, no skill, no `OnCreate`. JAR
  `CraftRecipeData.canOfferInputItem` / `offerInputItem`: an item is
  accepted on a line by the line's item list and flags; nothing reads an
  item's ModData. A handloaded round **is** `Base.Bullets9mm` (the assembly
  recipe's output is the vanilla type), so all nine rounds the mod makes
  can be boxed, and cartoned (`Place12BoxesInCarton`,
  `recipes_packing.txt`), with no mod code.
- **`IsExclusive`**: JAR `CraftRecipeData.offerInputItem` drops what is
  already on the line when an item of another full type is offered. One
  round type per box. Handloaded and factory rounds of one calibre are the
  same full type and mix freely.
- **Unboxing** (`OpenBoxOfBullets50`, `OpenBoxOfBullets20`,
  `OpenBoxOfShotgunShells`): `item 50 mapper:ammoTypes` and so on. The
  rounds that come out are **new items**.

### 3.1 Where the casing-quality record is lost

A handloaded round carries its casing quality in the item's ModData
(`AC_CaseQuality`). The record lives on the loose item only:

| Step | What vanilla does | Record |
|---|---|---|
| Round lies in an inventory or container | the item is saved with its ModData (JAR `InventoryItem.save`) | kept |
| `place_ammo_in_box` | consumes the round items, creates one box item; no `OnCreate` copies anything | **lost here** |
| `OpenBoxOf…` | creates 50, 20 or 25 fresh round items | nothing to restore |
| Loaded into a magazine or firearm | the round item is removed, a counter goes up (`ISLoadBulletsInMagazine`, `ISReloadWeaponAction`) | **lost here** |
| Unloaded | a fresh round item per count (`instanceItem`) | nothing to restore |

No attempt is made to carry the record through a box. A box holds a count,
exactly as a magazine does, and the box item is created by the engine with
no hook the mod could use without replacing vanilla's recipe. The
inspection text says so: "This record stays with the loose round; loading
or boxing it keeps only a count." Where quality could live once it is meant
to matter is in `AMMO_QUALITY_RUNTIME_DESIGN.md`.

### 3.2 What the mod does about boxes

- `calibre.box` and `calibre.roundsPerBox` in `AC_Calibres.lua` record
  vanilla's box for each round. Reference data: no recipe uses them.
- `tests/vanilla_snapshot.lua` records the recipe's item list, counts,
  mapper, `IsExclusive`, the absence of `OnCreate`, the unboxing recipes and
  the cartons; the tests compare the model with it and assert that the mod
  defines no box item, no box recipe, and no item tagged `base:ammo`.
- The game-start check probes each box item and the recipe id
  `place_ammo_in_box`, and reports `vanilla ammo boxes changed` if a build
  renames one. That affects boxing only; making and firing are untouched.

## 4. Component loot

Nothing beyond the die sets. See section 1.3: the components are the
manufacturing content, and their raw materials are vanilla loot already.
If rare component loot is ever wanted, `AC_Loot` is where it would go (an
entry is an item, a list and a weight), behind the same validation.

## 5. REQUIRES FUTURE IN-GAME VERIFICATION

- That `place_ammo_in_box` is offered for a stack of handloaded rounds
  (rounds carrying ModData), and for a stack that mixes them with factory
  rounds of the same calibre. Everything in the installed files says it
  is; it has not been seen.

- That an input line naming several items (`item 4 [A;B;C]`, no
  `IsExclusive` flag) is filled from a mix of them, as the scrapping
  recipes assume. JAR `CraftRecipeData.offerInputItem` only refuses a
  second item type on a line when the line is `IsExclusive`, so a line
  without the flag should mix. If it does not, a craft simply needs four of
  one component.
- That the four recycling recipes show at a surface and at a furnace and
  hand back the scrap and the ingot.

- That the `OnPreDistributionMerge` handler runs before the loot tables are
  parsed on a real world load, in single player and on a server. The log
  line `[AmmoMaking] Die set loot: 22 entries added, …` and the game-start
  check (`OK: die set loot (22 entries in 4 lists)`) say whether it did.
- That a die set actually appears in the four lists' containers, and how the
  weights feel against the sandbox loot settings.
- Containers generated before the mod was added keep what they have: only
  unexplored ones can hold a die set (INFERRED from loot being rolled when a
  container is first filled).
